--------------------------------------------------------------------------------
  1.  WHAT WE ARE BUILDING
--------------------------------------------------------------------------------

  One product, not a project per dataset.


   ┌──────────────┐       ┌───────────────────────┐       ┌──────────────┐
   │              │       │                       │       │              │
   │   ANY DATA   │──────▶│    THE MIDDLE LAYER   │──────▶│   BI  /  AI  │
   │    SOURCE    │       │                       │       │              │
   │              │       │   1  ontology         │       │  dashboards  │
   │  Postgres    │       │   2  knowledge graph  │       │  chatbots    │
   │  SQL Server  │       │   3  semantic         │       │  reports     │
   │  CSV files   │       │   4  context          │       │  agents      │
   │  Excel       │       │                       │       │              │
   └──────────────┘       └───────────────────────┘       └──────────────┘


  You connect a data source. It works out what is in there and hands the
  answer to whatever reads it.

  NOBODY WRITES CODE FOR A NEW DATASET. The same program reads a hospital
  database and a 121 MB shop export. That is the whole point.


--------------------------------------------------------------------------------
  2.  THE FOUR LAYERS
--------------------------------------------------------------------------------

  ╔════════════════════════════════════════════════════════════════════════╗
  ║  1  ONTOLOGY            what exists, and what is allowed               ║
  ║                                                                        ║
  ║     Reads the source and works out: what KINDS of thing are in here,   ║
  ║     how do you tell one from another, and what links them.             ║
  ║                                                                        ║
  ║     A table      -> a kind of thing     (customers -> Customer)        ║
  ║     Its key      -> how to identify one (customer_id)                  ║
  ║     A foreign key-> a link              (Order -> Customer)            ║
  ║     A date column-> when it was true    (order_purchase_timestamp)     ║
  ╚════════════════════════════════════════════════════════════════════════╝
                                    │
                                    ▼
  ╔════════════════════════════════════════════════════════════════════════╗
  ║  2  KNOWLEDGE GRAPH     what connects to what, over time               ║
  ║                                                                        ║
  ║     Every row becomes a thing. Every link becomes a line between two   ║
  ║     things. Every line carries a FROM and TO time, so the graph can    ║
  ║     be rewound to any moment.                                          ║
  ╚════════════════════════════════════════════════════════════════════════╝
                                    │
                                    ▼
  ╔════════════════════════════════════════════════════════════════════════╗
  ║  3  SEMANTIC            the numbers, defined once                      ║
  ║                                                                        ║
  ║     Works out what can be measured from the columns that are really    ║
  ║     there, and writes the SQL. One definition, so a number means the   ║
  ║     same thing in the dashboard, the report and the chatbot.           ║
  ╚════════════════════════════════════════════════════════════════════════╝
                                    │
                                    ▼
  ╔════════════════════════════════════════════════════════════════════════╗
  ║  4  CONTEXT             the packed answer                              ║
  ║                                                                        ║
  ║     Gathers facts from the three above, cuts them to a size an AI can  ║
  ║     actually read, and labels every line: did we MEASURE this, or did  ║
  ║     we WORK IT OUT?                                                    ║
  ╚════════════════════════════════════════════════════════════════════════╝


--------------------------------------------------------------------------------
  3.  THE ONE IDEA THAT MATTERS
--------------------------------------------------------------------------------

  A GUESS MUST NEVER LOOK LIKE A FACT.

      A real database declares its keys.  ->  the link is STATED    100%
      A CSV file declares nothing.        ->  the link is GUESSED    70%

  Both are shown, everywhere: in the tables, as a dashed arrow in the
  diagram, and in the final answer.

  If the two looked the same, nobody could tell which answers to trust -
  and the first wrong one would discredit all of them.

--------------------------------------------------------------------------------
  6.  HOW WE KNOW IT WORKS ON DATA WE HAVE NOT SEEN
--------------------------------------------------------------------------------

  Waiting for the next dataset to break it is not a plan, so the tests
  break it on purpose. 26 deliberately awkward sources, including:

      a table with no rows            a key that is unique by accident
      a table with no key at all      a column called "order" or "select"
      a key spread over two columns   names with quotes and accents
      a link pointing at nothing      a loop that would never end
      every value empty               120 columns
      mixed types in one column       two tables that clash after cleaning

  The rule is absolute: for ANY source, all four layers must FINISH.
  A thin answer is fine. A crash, a hang, or a graph that looks right and
  is wrong, is not.

  There is also a deterministic 100-table benchmark lake
  (benchmarks\fixture_lake100.py) with checked-in ground truth, so the
  before/after numbers are measured on the same data every time.

  A real 121 MB, 9-CSV export (the Olist shop data) completes end to end:
  1,550,922 things and 640,501 links, exit 0, and a second run reopens the
  graph warm instead of rebuilding it.


--------------------------------------------------------------------------------
  7.  HOW TO RUN IT  -  three commands
--------------------------------------------------------------------------------

  You need Python 3.10 or newer, from python.org.
  Tick "Add python.exe to PATH" during installation.

  Open PowerShell or Command Prompt IN THIS FOLDER and run:


      python -m pip install -r requirements.txt      (once, ~2 minutes)

      python run.py                                  see it in the terminal

      python run_server.py --port 8000               see it on a screen


  That is everything. No virtual environment needed, no `py` launcher -
  every one of those is a thing that can be missing
  on a locked-down machine, and each one has already cost an afternoon.

  If `python` is not recognised, Python is not on your PATH. Reinstall it
  from python.org and tick "Add python.exe to PATH", then close the window
  and open a new one.


  POINTING IT AT YOUR OWN DATA

      python run.py C:\myfiles\your.db
      python run.py C:\myfiles\csv_folder
      python run.py postgres://user:pass@host/dbname

  With no argument, run.py builds a small example shop and uses that, so a
  fresh copy always has something to show.

  In the UI, use Data sources and type the path there instead.


  SEEING THE SCREEN

      python run_server.py --port 8000

  then open   http://127.0.0.1:8000   in your browser.
  Press Ctrl+C in the terminal to stop it.

  External agents connect to the same server at  POST /mcp  with a key
  issued on the Agent connections page.


  CHECKING IT ALL WORKS  (optional, ~40 seconds)

      python -m pytest

      Expect:   all tests pass   (165 application tests, plus the
                benchmark-fixture tests)


  MEASURING IT  (optional)

      python benchmark.py --source data\example.db
      python benchmark.py --fixture lake100

      Prints connect / discover / build / query timings. The lake100
      fixture is generated first with:
      python benchmarks\fixture_lake100.py --out data\fixtures\lake100

--------------------------------------------------------------------------------
  9.  IF SOMETHING GOES WRONG
--------------------------------------------------------------------------------

  "python is not recognised"
      Python is not on your PATH. Install from python.org and tick
      "Add python.exe to PATH". Close the window and open a new one.

  "The packages are not installed yet"
      Run:  python -m pip install -r requirements.txt

  An import error naming something that clearly exists
      An old copy of the server is still running. Stop it and start again.

  "Port 8000 is already in use"
      Another server is running. Stop it, or pass --port 8001.

  "No Python 3.10 or newer found"
      Install from python.org and tick "Add python.exe to PATH". Close
      PowerShell, open it again.

  Tables look plain instead of sortable grids
      Expected on a locked-down machine. Windows Application Control
      blocks the library that draws them, so the app notices and draws
      simple tables instead of crashing.

  A large source feels slow the first time
      It is building the graph. Only the first time - after that it
      remembers. Press "Rebuild" in the sidebar to force it again.

  The database is locked
      DuckDB allows one writer at a time. Close other terminals,
      notebooks or editors touching the same file.


--------------------------------------------------------------------------------
  10.  WHAT IT CANNOT DO
--------------------------------------------------------------------------------

  It reads STRUCTURE from your data - tables, keys, types, dates. That
  part is automatic and needs nothing from you.

  It cannot read your BUSINESS NAMES. Nothing in a database says that a
  table called "tbl_cust_01" means Customer. It will call it Cust until
  somebody says otherwise.

  The discovery step accepts a rename map in code:

      discover(schema, names={"customers": "Buyer"})

  but run.py and the UI do not yet offer a place to store one. That is a
  known gap, not a feature that quietly works.

  Also not built yet: search over text, a review screen in the UI (the CLI and
  API gate exist), source-of-truth precedence between sources, a time-travel
  control in the UI (the graph and API already answer as-of), more connectors,
  and any wired-in AI. See SETUP.md for the full list.

  Multiple sources are supported now: pass several paths to run.py, or use
  connect_many/build_many in code. They share one graph, each row keeps its
  source, and ambiguous queries refuse to guess.

  The consumption surface exists: `python -m api.http` and
  `python -m api.mcp_server` serve ontology, graph neighbours, metrics and the
  Agent Context Builder. The review gate is `python -m review.cli`.

  This is a local prototype. There is no deployed instance, no support
  commitment, and no customer data.


================================================================================
  11.  WHAT CHANGED IN THE CORE (2026-10-29)
================================================================================

  Every source table is now materialised into the graph instead of relying on
  an attach that only happened during a build. That fixed the second-process
  crash ("s.<table> does not exist") for database sources: a warm graph now
  answers normally (verified in docs\benchmark\baseline\*_after_core.md).

  On top of that:
      - several sources can be built into one graph (source_id on every row,
        namespaced classes/relations/nodes, per-source rebuild);
      - a bad file in a folder is skipped with a warning instead of failing
        the source; duplicate file stems become distinct tables;
      - node ids include the source, so the same key in two systems is two
        nodes until cross-source resolution says otherwise.

  Cost: build time went from 6.0s to 8.1s on the 100-table lake because the
  graph now owns its data. That is the price of the warm path working.

  Then the capability core landed (2026-10-30):
      - cross-source identity candidates (`knowledge_graph/resolve.py`) with a
        confidence and an explanation; nodes are never merged silently;
      - human review gate (`review/`): propose, approve/reject, audit history,
        and a publish gate that refuses to serve semantic/context while an item
        is still pending (`python -m review.cli`);
      - Agent Context Builder (`context/assemble.py`): the entity, its links,
        cross-source matches and data-quality findings, packed under a hard
        budget with a citation per fact and a list of what was dropped;
      - API + MCP (`api/`): one service, served locally over HTTP and to agents
        over MCP stdio, with no new dependency;
      - the UI Context tab now uses the real pack builder and shows dropped
        facts and pending reviews.




================================================================================
  12.  WIDER SOURCES (2026-10-30)
================================================================================

  connect() now accepts, besides database files and CSV/Parquet/JSON/Excel:

      .nt / .nq              RDF graph files, streamed by DuckDB. Subjects and
                             IRI objects become Entity nodes; object properties
                             become Link nodes with two declared links to Entity.
      .ttl/.rdf/.jsonld      the same, via rdflib (optional install)
      http(s):// URLs        a supported file downloaded to a temporary folder
      snowflake:// URLs      via snowflake-connector-python (optional)
      databricks:// URLs     via databricks-sql-connector (optional)

  Measured on the 4.1 GB disamkb.nt knowledge-graph export:
      2,572,151 Entity + 18,293,623 Link nodes  = 20,865,774 things
      36,587,246 links, 0 dangling
      build 549 s, graph file 7.7 GB, exit 0
      the second run reopens the graph warm (no rebuild)

  A missing optional driver is reported with the exact pip command, not a
  stack trace. The graph records the failure as a finding when a source cannot
  be built.


  Triple-store folders (2026-10-30): a folder shaped like a CSKG export
  (entities.* + relations.* + triples/train/test/valid.*) is detected and read
  as a graph, not six unrelated tables. On data\raw\benchmark\cskg_dataset_sup_10:
      36,131 Entity nodes, 167 relation types, 132,286 typed edges (deduped
      across the train/test/valid overlaps), 0 dangling, build 5 s.
  Before this, the same folder produced 0 links.

  UI stale-server fix: `ui.py` now kills whatever is listening on port 8501 (and
  any python process running streamlit) before launching. The old wmic lookup is
  gone, which is why a server from D:\tushar\ontology could keep serving an old
  app and show `cannot import name 'table_ref'`.


  Concurrency fix (2026-10-30): the Graph now serialises every read with an
  RLock and consumes whole results instead of leaving a cursor open. The UI can
  read while another tab/request is in flight without DuckDB refusing with
  "connection is busy with another call". Verified on the 7.7 GB RDF graph:
  12 parallel count/class queries in 2.0 s. Regression tests:
  test_graph.py::TestConnectionReuse (sequential + 64 parallel reads) and
  test_app.py::TestRdfSource (the four tabs on an .nt source).


  Graph visual (2026-10-30): the Knowledge graph tab is now a named network.
  Each node shows its data label (`label`/`name`/`title`, key tail fallback),
  sized by connectivity, with white borders and curved edges; measured links
  are solid and derived links dashed. Layout can be force or circular.
  Regression tests: test_graph.py::TestSubgraphLabels and
  test_rdf_and_urls.py::TestGraphLabels.
