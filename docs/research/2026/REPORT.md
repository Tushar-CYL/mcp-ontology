# Governed semantics, not formats, make agents accurate

Strata's four-layer design (ontology, knowledge graph, semantic layer, context) plus agents matches the reference architecture that Microsoft, Palantir, NVIDIA, Snowflake, Databricks, dbt and Google all converged on in 2025-2026. The evidence says the value comes from **explicit, governed business meaning**, not from any particular format. In controlled paired studies, adding semantics lifts LLM accuracy on enterprise data by roughly **17 to 38 percentage points** (16% to 54% with a knowledge graph in 2023, 45-50% to 68% with a 4 KB definitions document in 2026, and 100% on in-scope questions with a compiled semantic layer). Just as important, governed layers **fail loudly**: they refuse or say "I don't know" where free text-to-SQL returns plausible wrong numbers. Nearly all of this evidence is vendor-run or vendor-linked, on 11 to 100 questions, so Strata should treat it as directional and build its own paired benchmark. For agents, the vendor pattern is **one orchestrator with a few small, typed, read-only tool bundles**, running under the end user's identity, not a fleet of separate agents. The practical recommendation is to keep Strata's deterministic schema-derived ontology, provenance labels, governed metrics, SQL validator and cited context packs; to add an explicit "answerable?" verdict with abstention, end-user identity on MCP, metric types and synonyms, full bitemporal edges, and open-format export (Apache Ossie YAML, Turtle/OWL); and to drop LLM document-extraction graphs, OWL reasoning, per-agent runtimes and write-back actions from the core product.

## Five parts, explained for someone who has never seen a schema

The cleanest way to explain Strata to a non-expert is a warehouse analogy, and every term maps onto a vendor definition. A **schema** is the shelf layout: bin numbers and aisle codes, which is how data is physically stored. The **ontology** is the product catalogue. It says what a "Customer" or an "Order" is and that a customer places orders, independent of storage. Microsoft defines its ontology as "a shared, machine-understandable representation of your business" covering concepts, properties, relationships and "the rules and metrics that give them business meaning," and says it bridges "the gap between how data is physically stored and how your business understands it" ([Microsoft Learn](https://learn.microsoft.com/en-us/fabric/iq/ontology/overview)). Palantir calls its ontology "the digital twin of an organization," built from object types and link types ([Palantir](https://www.palantir.com/docs/foundry/ontology/core-concepts)).

The **knowledge graph** is that catalogue with every real customer and order filled in and connected. A graph database is just one place to keep it: Timbr builds a "virtual knowledge graph over existing data sources using SQL-native ontologies" without storing the data ([Timbr docs](https://docs.timbr.ai/doc/docs/platform/)), so a DuckDB-backed graph like Strata's is a legitimate design. The **semantic layer** is the agreed accounting rulebook, "revenue = this formula, excluding returns," compiled into SQL so that every tool gets the same number. Databricks describes metric views as separating "measure definitions from the fields (dimensions) used to group, filter and aggregate" ([Databricks](https://docs.databricks.com/aws/en/metric-views/)). The **context** layer is the briefing folder handed to an analyst before a meeting: a few pages, each tagged with its source, with a note on what was left out. Anthropic defines context as "the set of tokens included when sampling from an LLM" and calls it "a finite resource with diminishing marginal returns" ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). **Agents** are the analysts who use the catalogue, the map, the rulebook and the folder to answer questions.

| Layer | Plain-language job | Question it answers | Strata today |
|---|---|---|---|
| Ontology | Catalogue of business things and how they relate | "What is a Customer, and how does it link to Orders?" | Tables to classes, PK to identity, FK to links, date to time, derived/measured labels |
| Knowledge graph | The catalogue filled in with real instances | "Which orders did customer C1 place, and what was true on 1 March?" | Rows in DuckDB, edges with provenance and valid-from, neighbours, multi-hop, as-of, cross-source identity |
| Semantic layer | Rulebook of approved calculations | "What was net revenue last quarter, by the certified definition?" | Governed metrics, approved/draft, owner, caveats, health, period comparison, SQL validator |
| Context | Small, cited evidence folder per question | "What exactly should the model see to answer this?" | Ranked, deduplicated, budgeted packs with citations, dropped-fact reasons, coverage score |
| Agents | Analysts that use all four | "Why did revenue drop, and can I trust the answer?" | Insight analyst runtime, MCP server with per-agent keys, review queue |

The boundaries are blurring. Apache Ossie (formerly Open Semantic Interchange) now calls itself "an open specification for both semantic layer and ontology," with separate working groups for metrics, catalog and ontology ([Dremio](https://www.dremio.com/blog/apache-ossie-the-open-semantic-interchange-joins-the-apache-incubator)). Microsoft's ontology item already holds entities, relationships, metrics, rules and bindings together ([Microsoft Learn](https://learn.microsoft.com/en-us/fabric/iq/ontology/overview)). No neutral body defines where one layer ends; the lines are drawn by vendor marketing. Strata should keep the four layers distinct in the UI, because that is easier to understand, but share entity IDs across them so they never become silos.

## Vendors agree on the chain but split on which layer leads

Every major vendor now describes the same pipeline: governed data, then a business model of metrics, then an ontology or graph of entities, then agent context, then agents over MCP. They differ on which layer is primary. **Metrics-first** vendors (dbt, Databricks, Snowflake) start from the semantic layer; **ontology-first** vendors (Palantir, Microsoft Fabric IQ, TextQL, NVIDIA) start from entities ([TextQL docs](https://docs.textql.com/core/ontology/overview); [NVIDIA auto-ontology](https://github.com/NVIDIA/auto-ontology)). Strata is ontology-first in derivation but metrics-first in governance, which is a reasonable hybrid.

### Ontology: virtual definitions bound to live sources

Microsoft Fabric IQ is the closest analogue to Strata. It generates an ontology from existing Power BI semantic models, turns DAX measures into metrics while "the source semantic model remains the owner of the DAX expression," binds definitions to live lakehouses and warehouses so the ontology is a "virtual semantic and context layer," attaches natural-language rules to entities, and uses an ontology agent whose "changes follow a proposal-first model" ([Microsoft Learn](https://learn.microsoft.com/en-us/fabric/iq/ontology/overview)). It keeps manual named versions and imports RDF, Turtle and OWL while exporting RDF and Turtle, so a large vendor treats W3C formats as an exchange format, not its internal model. Microsoft also made instance-graph materialization opt-in: "an ontology-derived schema graph doesn't load instance data by default," and routine lookups stay on source systems ([Microsoft Learn](https://learn.microsoft.com/en-us/fabric/iq/ontology/overview)).

Palantir remains the reference design for exposing an ontology to agents. Its ontology has "semantic elements (objects, properties, links) and kinetic elements (actions, functions, dynamic security)" ([Palantir](https://www.palantir.com/docs/foundry/ontology/overview)). In AIP Agent Studio an Object query tool filters, aggregates and traverses links over a chosen set of object types and properties, which also saves tokens, and an Action tool can require user confirmation ([Palantir tools](https://palantir.com/docs/foundry/agent-studio/tools)). Application variables let tools take inputs deterministically "instead of generating inputs dynamically through the LLM" ([Palantir application state](https://palantir.com/docs/foundry/agent-studio/application-state)).

NVIDIA's open-source auto-ontology (Apache-2.0, about 2,267 stars, pushed the day of research) is the only agent-native open project and the closest public match to an end-to-end lifecycle: **Discover** (ontology from metadata), **Ground** (business meaning for metrics, resolving inconsistent definitions), **Validate** (check generated queries against certified definitions and "return provenance with every answer"), **Expose** (MCP, CLI, API) and **Learn** (certified corrections) ([NVIDIA README](https://github.com/NVIDIA/auto-ontology)). Its MCP tools are all read-only, including `check_answerable`, `search_terms` and `ask_question`, and every write goes through a separate API surface with staged apply, certify, publish and roll back ([docs/mcp.md](https://raw.githubusercontent.com/NVIDIA/auto-ontology/main/docs/mcp.md); [AGENTS.md](https://raw.githubusercontent.com/NVIDIA/auto-ontology/main/AGENTS.md)). It stores credentials in plaintext unless Vault is configured and does not accept outside contributions, so it is a pattern source, not a dependency.

Snowflake has no product branded "ontology," but its rule is instructive: Cortex Analyst "will not join tables unless the semantic view explicitly defines the relationship" ([Snowflake guide](https://www.snowflake.com/en/developers/guides/best-practices-semantic-views-cortex-analyst/)). The relationship list is effectively the agent's join allow-list. Databricks Genie Ontology was reportedly announced at Data + AI Summit in June 2026 as a public preview that mines context from tables, dashboards and queries, but the official docs URL returned 404 and the claims come from secondary sources ([Kanerika](https://kanerika.com/blogs/databricks-genie-ontology/)). RDF-native vendors Stardog and Timbr stress OWL reasoning and virtual graphs ([Timbr FAQ](https://timbr.ai/timbr-faqs/); [Stardog](https://www.stardog.com/product/)), and ServiceNow bought data.world in May 2025 for its knowledge-graph catalog ([TechCrunch](https://techcrunch.com/2025/05/07/servicenow-acquires-data-world-two-months-after-acquiring-moveworks)).

### Knowledge graph: three families, and Strata is in the one with the evidence

Knowledge graphs come in three families. **Structured-to-graph** builds deterministically from relational data (R2RML, virtual graphs, data.world, Stardog, Timbr); it is cheap and has the only published enterprise question-answering accuracy evidence. **LLM extraction from documents** (Microsoft GraphRAG, LightRAG, AWS Bedrock GraphRAG) is expensive to index and its gains are disputed. **Temporal memory graphs** (Graphiti/Zep, Cognee) target agent memory; their best idea is bitemporal fact invalidation. Strata's row-to-node, FK-to-edge design belongs to the first family.

The document-extraction family is losing momentum. Microsoft's GraphRAG repo (MIT, about 36.5k stars) is in maintenance mode, "not an officially supported Microsoft offering," and warns that "indexing can be an expensive operation" ([microsoft/graphrag](https://github.com/microsoft/graphrag)). LightRAG (MIT, about 40.5k stars) is active, but its own LLM-judged win-rate table shows margins of only about 52-55%, and GraphRAG wins its "Mix" domain ([HKUDS/LightRAG](https://github.com/HKUDS/LightRAG)). Graph vendors meanwhile all shipped an agents-plus-MCP story: Neo4j puts a hosted MCP server in every Aura instance at no extra cost ([Neo4j](https://neo4j.com/blog/genai/introducing-mcp-for-aura/)) and offers Aura Agent with usage billing from 1 March 2026 ([Neo4j community](https://community.neo4j.com/t/new-release-aura-agent-ai-agents-from-your-auradb-knowledge-graphs/76481)); AWS made Bedrock GraphRAG on Neptune Analytics GA in March 2025 ([AWS](https://aws.amazon.com/about-aws/whats-new/2025/03/amazon-bedrock-knowledge-bases-graphrag-generally-available)); Glean launched an Enterprise Graph plus per-user personal graphs in September 2025 ([Glean](https://www.glean.com/press/glean-introduces-third-generation-ai-assistant-new-enterprise-graph-to-enable-the-superintelligent-enterprise)). Kuzu, once a popular embedded graph engine, was archived in October 2025 after Apple acquired it ([The Register](https://www.theregister.com/2025/10/14/kuzudb_abandoned/); [9to5Mac](https://9to5mac.com/2026/02/11/kuzu-database-company-joins-apples-list-of-recent-acquisitions/)), which vindicates DuckDB as Strata's embedded store.

Two graph capabilities matter most for agents. **Entity resolution** comes first: graphs without it accumulate duplicate nodes, and the recommended pattern links raw records to resolved entities rather than merging them ([KGC 2024](https://www.knowledgegraph.tech/blog/kgc-2024-knowledge-graph-named-entity-resolution/); [Neo4j + Senzing](https://neo4j.com/blog/knowledge-graph/entity-resolved-knowledge-graphs/)). **Temporal truth** comes second: Graphiti (Apache-2.0, about 32.5k stars) uses "explicit bi-temporal tracking with automatic fact invalidation," closing a superseded fact's validity window instead of deleting it ([getzep/graphiti](https://github.com/getzep/graphiti)). Strata's valid-from per edge is half of bitemporality; adding valid-to and recorded-at would let it answer "what did the agent believe on date X," which matters for audited evidence packs.

### Semantic layer: a native object everywhere, with AI metadata and MCP

The semantic layer became a first-class object in every major platform. dbt's MetricFlow has the richest metric typing (simple, ratio, derived, cumulative, conversion, and non-additive dimensions for balances) and was relicensed to **Apache-2.0 from version 0.209.0** at Coalesce in October 2025, after earlier AGPL and BSL phases; the hosted dbt Semantic Layer APIs stay commercial ([dbt blog](https://www.getdbt.com/blog/open-source-metricflow-governed-metrics); [GitHub metricflow](https://github.com/dbt-labs/metricflow); [dbt metrics](https://docs.getdbt.com/docs/build/metrics-overview)). Snowflake semantic views are native schema objects holding relationships, facts, dimensions, metrics, synonyms, sample values and verified queries ([Snowflake](https://www.snowflake.com/en/blog/engineering/native-semantic-views-ai-bi/)). Databricks metric views add "agent metadata" (synonyms, display names, formats), with relationships between views in Beta ([Databricks](https://docs.databricks.com/aws/en/metric-views/)). Power BI offers a remote MCP server for querying semantic models under the user's permissions and a local open-source modeling server, both in preview ([Microsoft Learn](https://learn.microsoft.com/en-us/power-bi/developer/mcp/mcp-servers-overview)). Looker's Conversational Analytics agent is GA and grounded in LookML, reachable through the open-source MCP Toolbox ([Google Cloud](https://cloud.google.com/blog/products/business-intelligence/looker-updates-for-agentic-bi-at-next26); [Looker MCP](https://docs.cloud.google.com/looker/docs/connect-ide-to-looker-using-mcp-toolbox)).

The common AI metadata set across vendors is description, synonyms, sample values, verified queries (question-to-SQL pairs), AI instructions and display format. Strata has description, format and caveats, but lacks synonyms, verified queries and explicit metric types. Those types matter because ratio, cumulative and non-additive metrics are where hand-written SQL most often goes wrong: dbt computes ratios as metric over metric, not as an average of ratios, and requires a `non_additive_dimension` so balances are not summed across time ([dbt metrics](https://docs.getdbt.com/docs/build/metrics-overview)).

The de facto agent tool pattern is **discover, inspect, then query**. dbt-mcp exposes `list_metrics`, `get_dimensions`, `get_entities`, `get_dimension_values`, `get_metrics_compiled_sql` and `query_metrics`, keeps discovery tools separate, and warns that its CLI tools "could modify your data models, sources, and warehouse objects" ([dbt-mcp](https://github.com/dbt-labs/dbt-mcp)). Cube Cloud's hosted MCP server has 30 tools, runs every tool as the authenticated user with row-level security, writes only to personal dev branches and asks for confirmation on nine destructive tools, while its own docs admit that a `chat` tool annotated read-only can still write ([Cube MCP docs](https://docs.cube.dev/docs/integrations/mcp-server)). None of the surveyed vendors exposes "check my SQL against the certified definition" as a standalone agent tool, which makes Strata's SQL validator a genuine differentiator.

### Context: every vendor sells a "context layer," mostly of metadata

By 2026 every data vendor sells a "context layer": a governed metadata graph plus semantic definitions, served over MCP with OAuth and permission passthrough. Atlan's remote MCP server has 29 tools, runs individual calls under the user's roles via OAuth, passes "only metadata" with no row data, reads live with no intermediate cache, and audit-logs tool calls ([Atlan MCP](https://atlan.com/mcp/)). Microsoft Foundry IQ plans subqueries, runs them under the caller's Entra identity and returns "grounded answers with citations," exposed through an MCP tool called `knowledge_base_retrieve` ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/what-is-foundry-iq)). DataHub's official MCP server requires each HTTP client to send its own token, with deliberately no server-wide token ([PyPI](https://pypi.org/project/mcp-server-datahub/0.8.0/)).

What vendors mostly deliver is metadata (definitions, lineage, ownership, certification) or document chunks. What Strata delivers is rarer: **measured numbers with segment contributions**, labelled measured or derived, plus a dropped-facts report and a coverage score. That combination is not advertised by any vendor in the research and is worth keeping. What Strata lacks, by comparison, is retrieval under the caller's own identity, OAuth on remote MCP, and certification status used as a ranking signal.

## Semantics add 17 to 38 points, but the studies are small and mostly vendor-run

The quantitative case for business semantics is consistent across four years, even as base models improved. In 2023, data.world's Sequeda, Allemang and Jacob found GPT-4 zero-shot reached **16% on an enterprise insurance SQL schema and 54% when asking over a knowledge-graph representation** of the same data ([arXiv 2311.07509](https://arxiv.org/abs/2311.07509)). Their 2024 follow-up added a deterministic Ontology-based Query Check and an LLM repair loop of up to three attempts, reaching **72.55% accuracy, about 8% "I don't know," and about 20% errors** ([arXiv 2405.11706](https://arxiv.org/pdf/2405.11706)). The point is not only accuracy: the ontology turned some wrong answers into explicit abstentions.

dbt Labs re-ran the same ACME Insurance dataset in April 2026 with 11 questions run 20 times each. Text-to-SQL rose from **32.7% (GPT-4, 2023) to 64.5%** (Claude Sonnet 4.6 and GPT-5.3 Codex), while the semantic layer scored **72.7% overall, 100% on in-scope questions, and 0% on the three questions needing too many entity hops**, because it declined to answer. After adding three LLM-generated dbt models, text-to-SQL climbed to 84-90% and the semantic layer to 98-100% ([dbt blog](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)). dbt's verdict is that "text-to-SQL fails silently" while the "Semantic Layer fails loudly," and its authors concede the text-to-SQL baseline got the full schema in context, which does not scale.

The 2026 paper by Rumiantsau and Fokeev tested 100 questions on Contoso Retail in ClickHouse with Claude Opus 4.7, Claude Sonnet 4.6 and GPT-5.4. A hand-written **4 KB markdown document** of measures, conventions and disambiguation rules raised accuracy from **45.5-50.5% to 67.7-68.7%** (+17 to 23 points, p<0.01), and within each condition the models were statistically indistinguishable, so the document "accounts for essentially all of the significant variance" ([arXiv 2604.25149](https://arxiv.org/abs/2604.25149)). The paper's PDF links to a benchmark repo under Cube's GitHub organization ([arXiv PDF](https://arxiv.org/pdf/2604.25149)), and Atlan cites it in its own marketing ([Atlan](https://atlan.com/know/ai-agent/semantic-layer/mcp-semantic-layer-for-ai-agents/)), so it is not clearly independent.

| Study | Setting | Without semantics | With semantics | Who ran it |
|---|---|---|---|---|
| data.world 2023 | Insurance SQL, GPT-4 | 16% | 54% (knowledge graph) | Vendor (data.world) |
| data.world 2024 | Same, + ontology check and repair | 54% | 72.55%, 8% "I don't know" | Vendor (data.world) |
| dbt 2026 | ACME Insurance, 11 questions x 20 | 64.5% | 72.7% all; 100% in scope; 0% out of scope | Vendor (dbt Labs) |
| arXiv 2604.25149 | Contoso Retail, 100 questions, 3 models | 45.5-50.5% | 67.7-68.7% (4 KB doc) | Vendor-linked (Cube repo) |
| Looker internal | Not disclosed | n/a | "Up to two thirds" fewer errors | Vendor (Google), unverified ([Google](https://cloud.google.com/blog/products/business-intelligence/looker-conversational-analytics-now-ga)) |

Two lessons follow. First, two different failure classes exist: **meaning errors** (wrong metric definition, wrong join) that semantic layers fix, and **coverage errors** (the semantic layer cannot express the question) that need graph traversal or validated SQL as a fallback. That argues for exactly Strata's combination of governed metrics, a graph for multi-hop questions, and a SQL validator for everything else. Second, the critics have a point: dbt's own data shows about 25 points came from better modeling alone ([Hackernoon](https://hackernoon.com/why-better-schema-modeling-beats-better-text-to-sql-models)), and a 4 KB text document captured most of the gain in the 2026 paper. The value is explicit business meaning, not a specific engine. TextQL argues that semantic layers are "a patch" confined to one warehouse, but its own chart compares GPT-4 in 2023 with Sonnet 4.6 in 2026, conflating model gains with layer gains ([TextQL](https://textql.com/blog/semantic-layers-are-a-patch-ontologies-are-the-fix)).

Public text-to-SQL leaderboards show what raw agents can do without a governed layer. On the official Spider 2.0 leaderboard read on 3 November 2026, the top **Spider 2.0-Snow** score is 96.70 (largely saturated), **Spider 2.0-Lite** tops out at 76.23, and **Spider 2.0-DBT** at 65.6; an AT&T and RelationalAI "Relational Knowledge Graph" entry scores 86.28 on Snow ([spider2-sql.github.io](https://spider2-sql.github.io/)). On BIRD the best system scores 83.40 against a human 92.96, and interactive, ambiguous tasks in BIRD-Interact top out at **16.33%** ([bird-bench](https://bird-bench.github.io/)). Those benchmarks are themselves noisy: a VLDB 2026 study found annotation error rates of **52.8% in BIRD Mini-Dev and 62.8% in Spider 2.0-Snow**, enough to reorder rankings ([Illinois Experts](https://experts.illinois.edu/en/publications/pervasive-annotation-errors-break-text-to-sql-benchmarks-and-lead/)). Strata should therefore not quote public leaderboards as proof; it should build a per-tenant golden set from approved metrics and verified queries.

Graph-over-documents evidence is weaker still. An independent re-evaluation found GraphRAG gains "much more moderate than reported previously" once LLM-judge bias and unrelated questions were removed ([arXiv 2506.06331](https://arxiv.org/abs/2506.06331)), and GraphRAG-Bench (ICLR 2026) is motivated by reports that GraphRAG "frequently underperforms vanilla RAG on many real-world tasks," helping mainly on complex multi-hop questions over large corpora ([arXiv 2506.05690](https://arxiv.org/abs/2506.05690v3)).

Context size has its own evidence. Chroma tested 18 models over 194,480 calls and found every one degrades as input grows, that a single distractor lowers accuracy, and that focused prompts of about 300 tokens beat full prompts of about 113k tokens for every model on LongMemEval ([Chroma](https://www.trychroma.com/research/context-rot)). Google's "Sufficient Context" work showed that retrieval makes models hallucinate rather than abstain when context is insufficient: Gemma's wrong-answer rate rose from **10.2% with no context to 66.1% with insufficient context**, and an LLM autorater can label sufficiency with at least 93% accuracy ([Google Research](https://research.google/blog/deeper-insights-into-retrieval-augmented-generation-the-role-of-sufficient-context/)). For ontology generation, the Burr benchmark (SIGMOD 2026, 54 real-world scenarios) reports "the current strengths of simple rule-based approaches compared to LLM-based systems" for learning ontologies from relational databases ([HPI](https://hpi.de/naumann/news/paper-accepted-at-sigmod-2026.html)), while the LLM pipeline RIGOR improves on naive prompting but was tested on only two medical databases with an LLM judge from the same family as one generator, and still produced classes with no backing column ([arXiv 2506.01232](https://arxiv.org/html/2506.01232v1)). That directly supports Strata's deterministic-first ontology.

What nobody has measured is equally important. No public benchmark measures citation accuracy or evidence-pack quality over structured data, no independent study compares a knowledge graph and a semantic layer on the same questions, and no study quantifies how often stale definitions or wrong joins cause production errors.

## Standards: MCP 2026-07-28, Apache Ossie v0.1, and W3C as exchange formats

**MCP's current protocol version is 2026-07-28.** The official versioning page says this revision replaced the initial handshake with per-request version negotiation through the `_meta` key `io.modelcontextprotocol/protocolVersion` and the `MCP-Protocol-Version` header, added a mandatory `server/discover` call, and keeps deprecated features for at least 12 months ([modelcontextprotocol.io](https://modelcontextprotocol.io/specification/versioning)). Cube's hosted MCP server independently states that it follows the 2026-07-28 spec ([Cube MCP docs](https://docs.cube.dev/docs/integrations/mcp-server)). The context-layer research note described 2025-11-25 as current, but it explicitly did not check for later revisions, so it is superseded on the version question. The 2025-11-25 revision still defines most of the security and tool rules a server must follow: OAuth with OpenID Connect discovery and Client ID Metadata Documents, incremental scope consent, input-validation errors returned as tool errors so the model can self-correct, and experimental tasks ([MCP changelog 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/changelog)). Its tools spec requires that servers validate inputs, enforce access control and sanitize outputs, lets tools declare an `outputSchema` with matching `structuredContent`, supports `audience`, `priority` and `lastModified` annotations, and warns that clients "MUST treat tool annotations as untrusted unless the server is trusted" ([MCP Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)). Its security guidance forbids token passthrough ("MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server") and recommends starting with minimal read scopes ([MCP Security](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)). Strata should serve 2026-07-28 while staying compatible with handshake-based 2025-11-25 clients.

MCP now sits under the Linux Foundation's Agentic AI Foundation, launched in December 2025 alongside goose and AGENTS.md; A2A v1.0 shipped in March 2026 with signed agent cards and reportedly joined the foundation in August 2026, though these details come from secondary sources ([Flowhunt](https://www.flowhunt.io/blog/agentic-ai-foundation-a2a-mcp-standards/)).

**Apache Ossie (Incubating)** is the semantic-layer standard to watch. Open Semantic Interchange launched on 23 September 2025, co-led by Snowflake, Salesforce, BlackRock, dbt Labs and RelationalAI ([BusinessWire](https://www.businesswire.com/news/home/20250923902448/en/Snowflake-Salesforce-dbt-Labs-Revolutionize-Data-Readiness)), and entered the Apache Incubator on **22 June 2026** as a "vendor-neutral format for expressing business metrics, dimensions, and their relationships" ([Apache Incubator](https://incubator.apache.org/projects/ossie.html)). It was renamed to avoid clashing with the Open Source Initiative, with the "core specification and its direction" unchanged ([GitHub discussion 164](https://github.com/open-semantic-interchange/OSI/discussions/164)). The spec is declarative YAML covering semantic models, datasets, fields, metrics, dimensions and relationships ([ossie.apache.org](https://ossie.apache.org/)), with converters for MetricFlow, Snowflake semantic models and Polaris, and a semantic *query* spec on the roadmap ([Snowflake](https://snowflake.com/en/blog/apache-ossie-open-semantic-interchange-incubator)). One note records the spec as v0.1; no release number appears on the pages cited. Databricks, Google and Microsoft were absent from the founder list, and their later participation is unknown.

**W3C standards matter at the edges.** The W3C Direct Mapping recommendation turns each table into a class, each row into an IRI built from its primary key, each column into a data property and each foreign key into an object property ([W3C Direct Mapping](https://www.w3.org/TR/rdb-direct-mapping/)). That is essentially Strata's rule set, so Strata's derived ontology is defensible as standards-aligned. R2RML generalizes this into custom mappings ([W3C R2RML](https://www.w3.org/TR/r2rml/)); SHACL validates graph shapes such as cardinality and required properties ([W3C SHACL](https://www.w3.org/TR/shacl/)); SKOS models glossaries with preferred and alternative labels ([W3C SKOS](https://www.w3.org/TR/skos-reference/)). The next versions are not finished: RDF 1.2 Concepts is a Candidate Recommendation dated 7 April 2026 ([W3C](https://www.w3.org/TR/rdf12-concepts/)), and SHACL 1.2 Core was still a Working Draft on 28 August 2026 ([W3C](https://www.w3.org/TR/2026/WD-shacl12-core-20260828/)). The practical stance, matching Microsoft's, is a native internal model with Turtle/OWL export, SKOS for synonyms, SHACL 1.0 shapes for validation rules, and no OWL reasoner or SPARQL endpoint unless customers ask.

## Failures cluster at joins, coverage, context size, identity and injection

The best practices across vendors fit on one line: generate a draft automatically, keep metrics owned by the semantic layer, require explicit relationships for joins, route all changes through review, keep named versions, and attach provenance to every answer. The failure modes are equally consistent, and each one maps to a Strata safeguard.

**Wrong or invented joins** are the classic meaning error. Snowflake refuses to join without declared relationships and does not directly support many-to-many ([Snowflake guide](https://www.snowflake.com/en/developers/guides/best-practices-semantic-views-cortex-analyst/)); Malloy's symmetric aggregates exist to stop join fan-out from double-counting ([Malloy](https://github.com/malloydata/malloy)); and a third party warns that Snowflake's Autopilot often adds no relationships at all on multi-table views ([The Data School](https://thedataschool.co.uk/jules-claeys/cortex-1-0-1-semantic-views/)). **Generated-ontology errors** include multiple domains or ranges on one property and untyped classes, both frequent in RIGOR's outputs ([RIGOR](https://arxiv.org/html/2506.01232v1)). **Coverage gaps** make a semantic layer score 0% on what it cannot model ([dbt](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)). **Drift and migration cost** show up in Microsoft's own warning that moving to its new ontology experience means reconnecting agents and recreating rules by hand ([Microsoft Learn](https://learn.microsoft.com/en-us/fabric/iq/ontology/overview)). **PII in sample values** is a documented Snowflake risk, alongside a semantic-model size limit of about 32K tokens ([phData](https://www.phdata.io/?p=24102)).

Context has its own four named failures, from Drew Breunig via LangChain: **poisoning** (a hallucination enters the context), **distraction** (too much context), **confusion** (superfluous context changes the answer) and **clash** (contradictory context) ([LangChain](https://www.langchain.com/blog/context-engineering-for-agents)). Anthropic's remedies are the smallest high-signal set, just-in-time retrieval through lightweight references, compaction, notes kept outside the window, and sub-agents that return 1,000-2,000-token summaries ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). For tools, Anthropic recommends a few non-overlapping tools, a `response_format` switch between concise and detailed (concise used about a third of the tokens in its Slack example), pagination, and actionable errors ([Anthropic tools](https://www.anthropic.com/engineering/writing-tools-for-agents)). The "lost in the middle" position effect ([arXiv 2307.03172](https://arxiv.org/abs/2307.03172)) was not replicated in Chroma's 2025 tests, which found "no notable effect" of needle position ([Chroma](https://www.trychroma.com/research/context-rot)); putting key facts first and last is a cheap hedge, not a law.

**Graph-specific failures** include duplicate nodes without entity resolution, stale facts without temporal invalidation, and super-nodes. Super-nodes are a design inference rather than a sourced finding: turning every low-cardinality value (country = "US", status = "active") into an edge creates hubs that explode multi-hop reach, so such columns should stay properties, and fan-out per hop should be capped.

**Prompt injection through data** is the most serious risk for a context layer, because sampled rows are exactly where untrusted text enters the prompt. In July 2025 a support ticket with hidden instructions led Cursor, using a Supabase MCP connection with a key that bypassed row-level security, to copy an `integration_tokens` table into an attacker-visible place; Simon Willison calls the combination of private data, untrusted input and an exfiltration channel the "lethal trifecta" and argues read-only access still carries risk ([Simon Willison](https://simonwillison.net/2025/Jul/6/supabase-mcp-lethal-trifecta/)). Invariant Labs named "tool poisoning" in April 2025 ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-tool-poisoning-ai-agent-exfiltration-2/)), CyberArk extended it to poisoned tool outputs with the warning that "no output from your MCP server is safe" ([CyberArk](https://www.cyberark.com/resources/agentic-ai-security/poison-everywhere-no-output-from-your-mcp-server-is-safe)), and Graphiti's own reference MCP server ships with no auth or injection protection ([graphiti](https://github.com/getzep/graphiti)). Prevalence figures for poisoned public servers conflict across sources and should not be quoted.

## The layers form one Discover, Ground, Validate, Expose, Learn loop

The layers are not a stack where each one simply sits on the one below. They form a loop, and NVIDIA's five verbs describe it well ([NVIDIA README](https://github.com/NVIDIA/auto-ontology)). In **Discover**, the ontology is derived deterministically from schemas, and the knowledge graph is filled with instances bound to those types; cross-source identity links records that represent the same real-world thing. In **Ground**, a user's words are mapped to ontology entities through descriptions and synonyms, and every number is routed to a governed metric that owns its formula, the way Microsoft keeps the semantic model as owner of each DAX expression ([Microsoft Learn](https://learn.microsoft.com/en-us/fabric/iq/ontology/overview)). In **Validate**, any query an agent writes is checked against the ontology's allowed joins and the semantic layer's certified definitions, then repaired or refused, the data.world pattern that moved accuracy from 54% to 72% and made 8% of answers honest abstentions ([arXiv 2405.11706](https://arxiv.org/pdf/2405.11706)). In **Expose**, the context layer assembles a small, cited, budgeted pack for the question and serves it, plus typed tools, over MCP. In **Learn**, corrections and approvals flow back through review into certified definitions, never automatically; commentators warn that "Learn" must not turn all feedback into rules ([besthub](https://www.besthub.dev/articles/nvidia-s-auto-ontology-90-faster-ontology-building-but-governance-remains-key-b83fd98bb262)).

Each layer contributes something the others cannot. The ontology supplies the join allow-list and the vocabulary. The graph supplies multi-hop and as-of answers, which is precisely where the semantic layer's coverage collapses to 0%. The semantic layer is the only thing allowed to compute a governed number. The context layer decides what the model actually sees and whether that is enough to answer. Agents orchestrate, but never bypass any of them. Strata's repository already reflects this loop in `semantic/validate.py`, `semantic/feedback.py` and `tests/integration/test_ground_validate_learn.py`, so the loop is a vocabulary the product can show non-experts directly.

## Agents: one orchestrator with typed tool bundles, not a zoo of agents

### What vendors actually ship

Vendors build three kinds of thing over enterprise data: structured-query agents (text-to-SQL, DAX or KQL grounded in a semantic model), retrieval agents over documents or ontology objects, and an orchestrator that routes between them and adds code execution, charts and actions. Snowflake Cortex Agents is one agent with typed tools: Cortex Analyst for text-to-SQL over semantic views, Cortex Search for documents, plus code execution, charting, custom tools and MCP connectors, all in a plan, use-tools, reflect loop shaped by natural-language planning and response instructions ([Snowflake](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents)). Microsoft's Fabric data agent is GA and read-only: it picks a source with the user's credentials, calls NL2SQL, NL2DAX or NL2KQL, validates and runs the query, and caps answers at 25 rows by 25 columns across at most five sources ([Microsoft Learn](https://learn.microsoft.com/fabric/data-science/concept-data-agent)). Databricks Agent Bricks put Genie text-to-SQL agents, a Knowledge Assistant and other tools under a supervisor capped at 50 subagents and tools, but that **Supervisor Agent is already marked "legacy … not recommended for new systems,"** with new builds pointed at Genie Agents and a CLI ([Databricks](https://docs.databricks.com/generative-ai/agent-bricks/multi-agent-supervisor)). Palantir offers Object query, Action, Command and Request clarification tools plus an "Ontology context" retrieval step that runs on every message and can emit citations ([Palantir retrieval context](https://palantir.com/docs/foundry/agent-studio/retrieval-context)). Looker's agents fetch the LookML schema of connected Explores at the start of each request ([Looker](https://docs.cloud.google.com/looker/docs/2606/conversational-analytics-overview)).

No vendor in the research markets a standalone "data guide" or "graph investigator" agent. Those jobs exist as tools or retrieval context inside one orchestrated agent. An academic survey confirms "data agent" is used loosely and places the frontier at the move from procedural (L2) to autonomously orchestrating (L3) systems on an L0-L5 scale ([arXiv 2510.23587](https://arxiv.org/abs/2510.23587)).

### Routing: one agent while the domain is narrow

LangChain's vendor-run benchmark on a modified Tau-bench found a single agent slightly better with one distractor domain but falling sharply with two or more; a supervisor suffered a "telephone" effect from paraphrasing subagent answers, and specific fixes (removing handoff messages, adding a `forward_message` tool) improved it by nearly 50% ([LangChain](https://www.langchain.com/blog/benchmarking-multi-agent-architectures)). Retrieving a shortlist of tools instead of listing all of them reportedly raised tool-selection accuracy from 13.62% to 43.13% in the RAG-MCP paper, though that figure comes from a secondary summary ([StackOne](https://www.stackone.com/blog/agent-tool-count-ceiling/)). Popular thresholds like "agents degrade after 10 to 15 tools" have no controlled study behind them. Both Fabric and Databricks route on developer-written descriptions of each source and tool ([Microsoft Learn](https://learn.microsoft.com/fabric/data-science/concept-data-agent); [Databricks](https://docs.databricks.com/generative-ai/agent-bricks/multi-agent-supervisor)), so Strata can generate those descriptions automatically from its ontology. External clients such as Claude, Copilot and Cursor will act as Strata's supervisor, which raises the bar on precise tool descriptions and small per-key toolsets.

### Agent types Strata should offer

The vendor evidence points to building agent types as **presets**: a restricted tool subset, a prompt and an output template, all running in one orchestrator runtime and each mapping cleanly to an MCP scope for external agents. Six presets cover the four layers and the trust question without overlapping.

| Agent type (preset) | Plain-language job | Layers and tools | Guardrails | Closest vendor analogue |
|---|---|---|---|---|
| Data Guide | "What data do we have, and what does it mean?" | Ontology: search terms, describe entity, list links, list metrics | Metadata only, no rows | dbt-mcp Discovery tools, NVIDIA `search_terms`, Atlan |
| Metric Analyst | "What is the governed number?" | Semantic: list/get metric, dimensions, dimension values (PII-masked), query metric, compare period | Approved metrics only; refuse with nearest metric otherwise | Cortex Analyst, Genie, Looker CA, dbt `query_metrics` |
| Entity Investigator | "Tell me everything about this customer, and what was true on date X" | Graph: neighbours, path, as-of, identity links | Fan-out cap, hop limit, scope per source | Palantir Object query with link traversal |
| Insight Analyst (orchestrator) | "Why did revenue drop?" | All four: trend, contributors, graph hops, context pack | Every number from a governed metric; validated SQL as fallback; abstain if insufficient | Cortex Agents, Fabric data agent, Agent Bricks |
| Trust Checker | "Can I trust this number?" | Semantic health, freshness, caveats, conflicts, provenance labels, coverage | Read-only, reports conflicts instead of resolving them | dbt `get_model_health`, Atlan certification |
| Steward (proposal-only) | "Suggest a missing link, synonym or metric definition" | Ontology and semantic drafts into the review queue | Never applies changes; human approval required | Microsoft proposal-first ontology agent, NVIDIA certify/publish |

The Data Guide and Trust Checker are the cheapest and safest to ship because they read only metadata. The Insight Analyst is today's in-app runtime and should be the orchestrator that the others are subsets of. Write-back or action agents, like Palantir Actions, should be deferred: they carry the highest risk and no Strata user need in the research requires them.

## Trust comes from refusal, the user's identity and a per-answer receipt

Across vendors the trust stack is the same: read-only execution, the caller's identity with row- and column-level security, a fixed source and tool scope, an instruction precedence that user prompts cannot override, labelled examples or verified queries, traces and feedback, and evaluation against golden questions. Fabric's precedence is explicit ("organizational intent > role-based intent > developer intent > user intent"), and instructions that try to bypass read-only or scope are refused ([Microsoft Learn](https://learn.microsoft.com/fabric/data-science/concept-data-agent)). Snowflake lets a run continue with only the tools the caller can access and adds per-run orchestration budgets, while disclaiming that answers and citations are guaranteed accurate ([Snowflake](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents)). Databricks asks the user to approve each web search and runs code in a sandbox with no internet and read-only table access ([Databricks](https://docs.databricks.com/generative-ai/agent-bricks/multi-agent-supervisor)). The archived Vanna v2 shows the same ideas in open source: tools declare `access_groups`, a `UserResolver` maps requests to users, and generated SQL is shown only to admins by default ([Vanna](https://github.com/vanna-ai/vanna)).

Three things would make Strata's agents more trustworthy than the vendor norm. The first is **explicit refusal**. Vendors document refusal mostly for policy conflicts, and none in the research quantifies abstention. The evidence that insufficient context drives hallucination (Gemma 10.2% to 66.1%) and that ontology checks convert errors into "I don't know" makes an `answerable: yes | partial | no` verdict with a reason a first-class output. The second is **end-user identity**. Every vendor runs agents as the caller (Fabric with user credentials, Snowflake with the caller's role, Atlan and Foundry IQ via OAuth), while per-agent keys alone cannot enforce per-user row security. The third is a **per-answer layer receipt** in plain language, for example "used: Ontology (Order), Semantic (net_revenue v3, approved), Graph (customer C1, 2 hops), Context (5 cited rows, 3 dropped)." Vendors expose provenance as retrieval citations and builder-facing diagnostics; a layer-level receipt for non-experts is not a documented feature anywhere.

Evaluation should follow Anthropic's advice to test on realistic multi-step tasks and track accuracy, tool calls, runtime, tokens and errors on held-out sets ([Anthropic tools](https://www.anthropic.com/engineering/writing-tools-for-agents)), with RAGAS-style metrics for context precision, recall, faithfulness and tool-call accuracy ([RAGAS](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)). Strata's specific evals should be paired accuracy with and without each layer, citation accuracy (every claim maps to a fact ID), faithfulness (no numbers absent from the pack), agreement between the coverage score and an LLM sufficiency autorater, abstention correctness on unanswerable questions, and tokens per correct answer. Judging must be blind or position-swapped, because judge bias inflated GraphRAG's reported gains ([arXiv 2506.06331](https://arxiv.org/abs/2506.06331)).

## Implications for Strata

The goal is a product a non-expert can understand in one sentence per layer: **Strata turns any data source into a catalogue (ontology), a connected map (knowledge graph), a rulebook of approved numbers (semantic layer) and a cited briefing folder (context), and then gives you agents that use all four and tell you when they cannot answer.** Anything that does not fit one of those five nouns should leave the main navigation. The review queue stays, but as the shared "approve" step that appears inside each layer, not as a separate destination.

### Keep, because the evidence supports it

The **deterministic schema-derived ontology** is the strongest choice in the product. It matches the W3C Direct Mapping standard, and the Burr benchmark found rule-based methods still beat LLM ontology learning. The **derived and measured provenance labels** have no direct equivalent in Microsoft's or Snowflake's docs and map neatly onto the industry's proposal-to-certified flow. The **DuckDB knowledge graph** built from structured rows sits in the only graph family with enterprise accuracy evidence, and avoids the Kuzu trap. **Cross-source identity** should stay as explicit, reversible same-as edges that never merge source rows. The **governed metrics with status, owner, caveats and health** match every vendor's core fields. The **SQL validator** is the clearest differentiator, the productized version of data.world's ontology check. **Context packs with citations, dropped-fact reasons and a coverage score** follow every principle from Anthropic, Chroma and Google. The **read-only MCP server with per-agent scopes and a usage log** is aligned with Atlan, DataHub and NVIDIA.

### Build, in roughly this order

| Priority | Build | Why |
|---|---|---|
| 1 | `answerable: yes / partial / no` with a reason, derived from the coverage score, and explicit refusal with the nearest approved metric | Insufficient context drives hallucination; ontology checks turn errors into abstentions; vendors under-document refusal |
| 2 | End-user identity on MCP (OAuth, audience-checked tokens, no token passthrough) on top of per-agent keys | Every vendor runs agents as the caller; required by the MCP security guidance |
| 3 | MCP 2026-07-28 support with `server/discover`, `outputSchema` and `structuredContent` for packs, metrics and entities as resources usable as citation targets, `lastModified` on every fact, backward compatibility with 2025-11-25 | Current protocol; protocol-native freshness and citation fields |
| 4 | Agent presets (Data Guide, Metric Analyst, Entity Investigator, Insight Analyst, Trust Checker, Steward) in one runtime, each mapping to an MCP scope | One orchestrator beats multi-agent while the domain is narrow; least-privilege per key |
| 5 | Per-answer layer receipt in plain language | Not offered by any vendor reviewed; makes provenance readable for non-experts |
| 6 | Semantic-layer upgrades: metric types (ratio, cumulative, derived, non-additive), synonyms, verified queries, PII-masked dimension values, named versions with change history | Where hand-written SQL goes wrong; the common AI metadata set across vendors |
| 7 | Explicit join allow-list with cardinality; only measured or certified links usable for joins by default; collapse junction tables into many-to-many links | Snowflake-style strictness prevents invented joins and over-modelling |
| 8 | Full bitemporal edges (valid-to, recorded-at) and super-node guards (low-cardinality columns as properties, fan-out caps) | "What was true on date X" and "what did we believe then"; prevents multi-hop explosion |
| 9 | Injection fencing: sampled row text delivered as typed, delimited data; no write or egress tools in the same session | The lethal trifecta lives in the context layer |
| 10 | Paired evaluation harness: re-run the ACME insurance questions with and without each layer, blind or position-swapped judging, citation and abstention metrics | All public numbers are vendor-run; Strata needs its own |
| 11 | Open-format export: Apache Ossie YAML for metrics, Turtle/OWL via rdflib and SKOS labels for the ontology, SHACL 1.0 shapes for validation rules | Cheap interoperability and a credible "open" answer to buyers |

### Drop or defer

**LLM document-extraction graphs** (GraphRAG-style) should not be part of the core: indexing is expensive, the upstream reference is in maintenance mode, and the gains shrink under unbiased evaluation. Offer document extraction later, if at all, as an optional connector. **OWL reasoning and a SPARQL endpoint** are used mainly by RDF-native vendors and academia; export is enough. **Materializing a node for every fact row** duplicates the warehouse; Microsoft made instance materialization opt-in, so materialize entity tables and treat fact rows as edges or properties. **Separate agent runtimes per agent type** should collapse into presets over one orchestrator. **Write-back and action agents** should be deferred. **Mem0-style per-user conversational memory** belongs to the client, not to a governed data context layer. **Trend and contributor analysis** should move from the semantic layer into the Insight Analyst agent, since no surveyed vendor treats them as semantic-layer features (a judgement call, not a sourced finding). **Automatic learning** that turns feedback into rules without review should never ship.

## Conclusion

The research changes what Strata should claim. Strata should not say "we have an ontology and a knowledge graph" as though the formats were the product. Its claim is narrower and easier to defend: **every number comes from an approved definition, every join from an allowed link, every answer carries a receipt, and the agent says so when it cannot answer.** The evidence for accuracy gains is real but vendor-produced; the evidence that governed layers turn silent wrong answers into honest refusals is the more durable finding, and it is the one no competitor has made into a visible product feature. Strata's deterministic, provenance-labelled design is unusually well placed to make it one.

The market also signals that it is still moving. Databricks retired its supervisor within a year, Microsoft rebuilt its ontology model in preview and made instance graphs optional, Kuzu disappeared, GraphRAG froze, and MCP changed its version handshake. The safest strategy is to own the semantics and keep the plumbing replaceable: one runtime with presets instead of an agent zoo, open export formats instead of lock-in, a standard protocol at the edge, and a private paired benchmark that measures Strata's own layers rather than borrowing someone else's numbers.
