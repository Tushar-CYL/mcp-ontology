================================================================================
  1.  WHY WE ARE DOING THIS
================================================================================

  Our company has already seen one version of this.  It was built inside
  DATABRICKS.  All four layers, plus charts on top.  It works.

  It also costs money every hour it runs.

  The manager asked for R&D, not one more project.  R&D means: try it
  several different ways, measure each way, and report which way is best
  for which situation.

  So the question is not "can we build it?"  We already did, once.

  The question is:

        Which tools should we use for each layer?
        What does each tool really give us?
        How much does it cost?

  And one answer we want to be able to PROVE:

        "Here is a version you can use for free."

================================================================================
  4.  WHY TIME ON EVERY LINK MATTERS
================================================================================

  This is the single best thing to demo.  Every link stores a FROM time
  and a TO time, so the whole graph can be rewound to any moment.


      time ──────────────────────────────────────────────────────▶
             00:00         00:01         00:02         00:03

      C_1 runs_on NODE_A  [====================]

      C_1 runs_on NODE_B                        [=================]


      Question: "Where is C_1 at 00:01:30?"      Answer: NODE_A
      Question: "Where is C_1 at 00:02:30?"      Answer: NODE_B


  Same question.  Different moment.  Different correct answer.

  ALREADY PROVEN ON THE REAL DATA:
  blast radius for one node returns 2,591 services at 00:01:00
  and 2,055 services at 00:02:30, in about 0.1 seconds.
  The system genuinely changed in between, and the graph knows it.

  1,089 rows in every file are broken.  A normal bulk load either

  WHAT THIS ALREADY TELLS US, BEFORE WRITING ANY CODE
  ────────────────────────────────────────────────────────────────────

  NEITHER DATABRICKS NOR SNOWFLAKE IS A GRAPH DATABASE.
  Both do layer 2 by putting rows in a table and walking them with
  Spark or SQL.

  So the strongest point in our pitch is not "we are cheaper".  It is:

        "For the graph layer, the FREE tool is the BETTER tool."

  Neo4j is in the plan to prove, or disprove, exactly that.

  THE FIVE QUESTIONS, ASKED IDENTICALLY IN ALL FOUR ARMS

    1.  If NODE_12426 dies right now, which services are hit?
        (blast radius)

    2.  Where has container C_1 been running, and when did it move?
        (placement history)

    3.  Which services sit on the most critical paths?
        (choke points)

    4.  What was the p99 latency of MS_5261 in this minute?
        (one metric)

    5.  Why was MS_5261 slow at 00:02:30, and who should be paged?
        (needs ALL FOUR LAYERS at once — this is the real test)



================================================================================
  10.  WHAT WE HAVE ALREADY FOUND  (ARM D)
================================================================================

  This is the part that justifies the R&D to a manager.
  Every item below was found by A RULE FAILING, not by reading docs.


  THE PUBLISHED DOCUMENTATION IS WRONG IN TWO PLACES
  ────────────────────────────────────────────────────────────────────
  It says one field appears only for certain call types.
      -> Every single row has it.
  It says some rows carry a negative response time.
      -> There are zero.

  Code written from the documentation would be silently wrong.


  REAL FAULTS IN A WIDELY USED PUBLIC DATASET
  ────────────────────────────────────────────────────────────────────

     1,089      broken rows per file       one of them crashes a
                                           normal bulk load

     2,012,289  orphan rows  (15%)         only 43.3% of traces
                                           have a root at all

       188,643  response times written     read as 0, they drag
                as the text "None"         every average down

       255,067  rows where the ID          the name and the ID
                contradicts its own name   disagree with each other


  THE ONTOLOGY CAUGHT BUGS IN OUR OWN CODE
  ────────────────────────────────────────────────────────────────────
  34,594 links pointed at the wrong KIND of thing.
  10,969 links pointed at IDs that were never created.

  A walk through a broken link does not crash.  It just returns less
  and looks perfectly healthy.  Only a declared rule finds it.


  A HIDDEN IDENTITY BUG
  ────────────────────────────────────────────────────────────────────
  The default hash function gave 5,878 COLLISIONS in 921,622 keys.
  Chance says about 1 in 20 million.  Container IDs share long
  prefixes, which broke it.  Switching the hash: ZERO collisions.
  A key constraint caught it.


  THREE OF OUR OWN RULES WERE WRONG, AND MEASURING FIXED THEM
  ────────────────────────────────────────────────────────────────────
  One fired on 52% of all rows.  The RULE was wrong, not the data.
  A rule that fires on half the data hides every real signal next
  to it.



================================================================================
  11.  WHAT WE DELIBERATELY DID NOT BUILD
================================================================================

  Say this before anyone asks.  It is credibility, not a gap.


  THERE IS NO ERROR RATE METRIC.
  This data has no status codes, so an error rate cannot be worked out
  from it.  Inventing one would be a fake number wearing a real name.
  We use SLOW CALL RATE instead, with the threshold as a setting the
  caller chooses, never hidden inside the definition.


  TEAM OWNERSHIP IS A GUESS, NOT A FACT.
  The data has no org chart.  We work teams out from the call pattern.
  So every team is tagged "derived", and that tag shows up in the
  final answer.



================================================================================
  12.  TOOL RESEARCH DONE SO FAR
================================================================================

  Done before planning.  These already changed the plan.


  KUZU  (embedded graph database)
      Archived October 2025 after Apple bought the company.
      Forks exist (LadybugDB and others) but they are young.
      -> Do not build on it.  Keep it as a risk story: free tools
         can disappear.

  CUBE CORE  (the best known free semantic layer)
      Ships as Docker only.  No supported Windows install without it.
      -> Ruled out by our no-Docker rule.  Use dbt + MetricFlow.

  DUCKDB VECTOR EXTENSION
      Still labelled experimental.  Saved indexes need an opt-in
      experimental flag.  The docs say do not use in production.
      -> Use Qdrant or LanceDB in the free arm.

  DBT SEMANTIC LAYER
      Free to WRITE metrics.  PAID to SERVE them to a BI tool or an
      agent.  MetricFlow itself is Apache 2.0.
      -> Name this trap in the report.  A buyer would miss it.

  PYSHACL
      The slowest SHACL engine in published comparisons, and it
      scales badly with size.
      -> Expect it to lose to SQL rules at 1.5M links.  Measuring
         that is a RESULT, not a failure.

  NEO4J COMMUNITY
      GPLv3, free, ships a Windows ZIP, needs no Docker.
      Limits: one database, no role based access, a slower query
      runtime than the paid Enterprise edition.
      -> Good fit.  State the limits plainly in the report.

  FREE DATA CATALOGUES  (OpenMetadata, DataHub)
      Nearly all assume Docker.
      -> A finding in itself: "free" often quietly means
         "free if you run Linux containers."
